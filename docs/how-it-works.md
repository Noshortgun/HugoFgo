# 工作原理

这份文档用一次 FGO 刷本解释 HugoFgo 的各个部分。你可以先了解每个模块在游戏过程中负责什么，再按需进入接口和协议细节。

这里描述当前实现，不代替[架构与接口](architecture.md)、[当前状态](status.md)和[领域术语](../GLOSSARY.md)。

本文截图来自项目已入库的实机关键帧，只做轻度模糊和缩放。图注用于解释模块分工，不构成新的实机验收证据。

## 1. 一次刷本涉及哪些部分

```text
你安排编队与每回合操作
          │
          ▼
┌─────────────────────┐
│ 前端 UI              │  编辑作业、展示进度
└──────────┬──────────┘
           ▼
┌─────────────────────┐
│ 桌面壳 Shell         │  保存作业、检查设备、启动执行器
└──────────┬──────────┘
           ▼
┌─────────────────────┐
│ 作业模型 Job Model   │  把作业编译成执行计划
└──────────┬──────────┘
           ▼
┌─────────────────────┐      观察      ┌─────────────────────┐
│ 执行器核心 Executor  │ ◀──────────── │ 画面感知 Perception  │
└──────────┬──────────┘               └──────────▲──────────┘
           │ 点击、滑动                           │ 截图
           │                              ┌──────┴──────────────┐
           │                              │ 安卓模拟器中的 FGO   │
           │                              └──────▲──────────────┘
           ▼                                     │
┌─────────────────────┐                          │
│ 设备网关 Device      │ ─────────────────────────┘
└─────────────────────┘

执行器核心 ──事件──▶ 运行会话 Run Session
                      保存结果、摘要和画面证据
```

最重要的关系是：**作业模型决定“计划做什么”，画面感知报告“现在看到了什么”，执行器核心决定“下一步是否可以安全执行”，设备网关负责实际输入。** 任何一环无法确认，都不能由另一环靠猜测补上。

## 2. 前端与桌面壳：从你的安排到一次运行

### 游戏情景

你在“编队”工作区安排从者和操作序列，设置刷本次数与 AP 恢复方式，然后点击“战斗”。运行后，你又在面板里看到当前面、回合和动作。

### 软件在做什么

前端负责四件事：

- **准备**：管理设备、区服、图库和设备通道。
- **编队**：编辑从者、操作序列、选卡策略、刷本次数和 AP 设置。
- **运行**：启动、停止并展示真实事件。
- **记录**：查看历史结果与证据。

桌面壳负责这些界面背后的本地工作：保存作业和设置、查询设备、启动唯一的执行器子进程、转发运行事件，以及定位历史文件。

浏览器预览只有界面能力，没有桌面壳提供的设备和真实运行功能。

### 为什么这样分工

界面不应直接实现战斗规则。这样无论用户从编队页还是运行页启动，进入的都是同一个执行器；运行历史也来自真实事件，而不是界面自行编造的进度。

模块与命令契约见[架构与接口](architecture.md)。

## 3. 作业模型：把手动打法变成执行计划

### 游戏情景

假设你的打法是：第 1 面先使用充能技能，再放指定从者的宝具；如果敌人没有退场，就按卡色和暴击率补刀。换人或从者退场后，后续动作仍应作用于原来的指定从者，而不是单纯点击屏幕上的同一个位置。

### 软件在做什么

作业模型读取 JSON，检查结构和引用，再把编队、面、回合、动作和选卡策略展开成执行计划。

其中几项规则直接影响游戏操作：

- 作业用 0–5 号槽位标识从者，不用一次界面会话里的临时身份。
- 空槽位表示不限定身份，不要求游戏内该位置为空。
- 主动换人与自动补位后，程序另行维护从者当前所在位置。
- 宝具卡序和普通指令卡策略是不同规则。
- 作业可以保存当前执行器不支持的内容，但编译与能力检查会在启动前拦截。

### 为什么需要编译检查

“文件格式正确”只说明字段能够解析，不表示游戏动作已经受支持。例如，技能追加选择必须带完整候选，且索引与所选值一致；旧格式或数据不完整时执行器会在启动前拒绝。提前报告问题，比进入战斗后跳过动作更安全。

字段语义见[作业格式](job-format.md)，机器契约是 `schemas/job-v1.schema.json`。

## 4. 画面感知：读懂当前游戏画面

### 游戏情景一：选择助战

助战列表里可能同时出现相同从者、不同再临或灵衣，以及不同概念礼装。程序需要找到作业要求的组合，而不是只认出一行文字。

![FGO 助战选择页，显示职阶页签和多行助战候选](assets/how-it-works/support-selection.jpg)

*图 1：助战选择页。程序不仅要认出从者，还要核对概念礼装，并根据列表内容决定选择、翻页或刷新。*

当前感知使用头像区域与概念礼装图库匹配身份，不使用文字 OCR 选择助战。普通再临和灵衣会归一到同一个从者身份。找不到目标时，执行器按规则翻页或刷新，不会在列表里随便选一个。

### 游戏情景二：核对编队

进入队伍确认页后，作业要求的从者是否真的在对应槽位？助战是否带着要求的概念礼装？御主礼装是否正确？

![FGO 队伍确认页，显示六个编队位置、概念礼装和开始任务按钮](assets/how-it-works/team-confirmation.jpg)

*图 2：队伍确认页。只有作业指定的从者、助战概念礼装和御主礼装通过核对，程序才会点击“开始任务”。*

感知分别读取这些字段。只要指定项不符或持续无法确认，执行器就不会开始任务。空槽位不参与指定身份核对，因为它本来就不限制实际从者。

### 游戏情景三：读取指令卡

进入选卡页后，程序需要知道五张普通卡分别属于谁、是什么颜色，以及哪些宝具可以使用。技能特效、飞卡或短暂遮挡都可能让某一帧不可靠。

![FGO 指令卡选择页，显示一张宝具卡和五张普通指令卡](assets/how-it-works/command-cards.jpg)

*图 3：指令卡选择页。上方是宝具卡，下方是五张普通卡；程序分别判断从者身份、卡色和可用状态，再按作业选择三张。*

感知会返回身份、卡色和控件等观察。信息不足时，执行器会等待后续画面，并按规则结合多帧证据；不能安全选出卡片时就停止，而不是沿用旧坐标盲点。

### 为什么感知只报告观察

感知负责“看到了什么”，不决定“下一步点什么”。同一份观察可以用于实机执行和离线回放，执行器不需要直接处理像素。

观察还区分“不需要读取”“尚未读取”“无法确认”和“已经确认”。未知不是空值，也不能自动当成可用。

识别范围、算法和当前限制见[架构与接口](architecture.md)与[当前状态](status.md)。

## 5. 执行器核心：决定下一步，并确认动作结果

### 游戏情景一：技能动画还没有结束

玩家点击技能后，游戏可能播放动画、要求选择目标，或者短暂保留旧画面。点击已经发出，并不代表下一项操作现在就可执行。

![FGO 战斗页，显示从者技能冷却、当前敌人和攻击按钮](assets/how-it-works/battle-ready.jpg)

*图 4：技能流程结束后的战斗页。程序需要重新确认当前画面和技能状态，不能因为技能点击已经发出就立即点击“攻击”。*

执行器因此反复进行：

```text
读取画面 → 选择当前动作 → 发送输入 → 等待并重新读取 → 确认后再推进
```

技能是否进入冷却、目标选择是否完成、攻击是否进入选卡页，都有各自的确认与恢复边界。程序不会只靠固定等待时间连续点击。

### 游戏情景二：作业动作没有清场

预定技能和宝具已经执行，但敌人仍在场。执行器按补刀策略继续选卡，不会擅自使用未编排的技能。

如果实际战斗已经偏离计划，原动作无法执行，但画面和可用操作仍能确认，当前场可以进入计划外自动战斗。程序会告知原因，下一场恢复原始作业。若画面或安全操作目标也无法确认，则安全停止。

### 游戏情景三：AP 用尽

连续出击前出现 AP 恢复页时，执行器只使用白名单允许的道具。确认框中的道具必须和待确认项目一致。

![FGO 青铜果实恢复确认框，显示消耗数量和决定按钮](assets/how-it-works/ap-recovery.jpg)

*图 5：青铜果实恢复确认框。即使作业允许使用青铜果实，程序仍要核对弹窗中的道具，不能把“出现了确认框”当成可以无条件点击“决定”。*

例如，白名单为空时，程序不会因为圣晶石可用就自行选择，而是停止并保存证据。固定场数完成后的清 AP 阶段也不使用任何恢复道具。

### 为什么坚持安全停止

自动化的目标不是让点击永不中断，而是只在操作条件明确时继续。未知页面、意外弹窗、身份不明或进度不确定时，少点一次通常比误用道具、选错目标或重复技能更安全。

完整状态机和恢复规则见[架构与接口](architecture.md)与[需求基线](requirements.md)。

## 6. 设备网关：把决定变成模拟器里的操作

### 游戏情景

执行器决定点击某张指令卡，但模拟器的实际分辨率可能与作业的基准坐标不同。此时不能直接发送一个固定像素坐标。

### 软件在做什么

设备网关提供截图、点击和滑动。动作以 1280×720 为基准，由设备适配器换算到真实分辨率。只有精确 16:9 横屏且不低于 1280×720 的画面才会被接受，避免拉伸比例不同导致错点。

当前默认通道是 scrcpy。启动失败且用户允许回退时，可以明确改用 ADB；运行中通道中断则安全停止，不在另一种通道上接着盲点。

桌面壳的 adb 截图用于设备预览，战斗中的高频截图和输入由执行器自己的设备层完成。

协议与适配器边界见[架构与接口](architecture.md)。

## 7. 运行会话：留下能够复盘的事实

### 游戏情景

一场刷本停在第 2 面。你想知道程序原本准备做什么、实际点击了什么、游戏是否确认进入下一状态，以及最后看到了哪张画面。

![FGO 掉落奖励页，显示本场获得的战利品](assets/how-it-works/run-result.jpg)

*图 6：掉落奖励页可以说明游戏到达了结算流程，但不能单独证明每个计划动作都已执行。完整复盘还要结合动作事件、后续画面确认和最终结果。*

### 软件在做什么

运行会话保存事件、结果和必要画面，并生成中文动作摘要。摘要按场、面、回合和动作组织，区分：

- 已向设备发送输入。
- 后续画面已经确认。
- 该动作没有独立的生效确认。
- 计划中的动作没有执行。

`action` 事件只说明输入已经发送，不能单独证明游戏受理。`result.json` 记录最终结果，原始 `events.jsonl` 保留事件顺序，`summary.md` 供人复盘，失败画面帮助定位停止时的游戏状态。

需要手动接管时，停止在当前动作边界生效。运行证据的用途和文件说明见[使用指南](user-guide.md#6-查看记录与故障证据)。

## 8. 把常见术语放回游戏中

| 术语 | 在一次刷本中的含义 |
| --- | --- |
| 作业 | 编队、每面每回合的操作和选卡规则的完整定义 |
| 面 | 一波敌人；一个关卡最少一面、最多三面 |
| 回合 | 一面内从技能安排到选卡攻击的一次操作周期 |
| 补刀策略 | 预定动作没有清场时，继续选目标和选卡的规则 |
| 计划偏离 | 实际战斗与作业预期不同，但不一定需要停止 |
| 计划外自动战斗 | 原动作无法执行时，为完成当前场而采用的自动战斗模式 |
| 安全停止 | 无法安全确认操作时停止，并保存定位问题所需的证据 |
| 回放 | 用已采集截图离线验证执行器，不接触真实设备 |

这里是导读摘要，严格定义以[领域术语](../GLOSSARY.md)为准。

## 9. 当前能力边界

理解架构不等于所有模块已经在所有场景中验收：

- 当前执行器只接受国服。
- 实机证据集中在指定种火作业、模拟器和分辨率，不能推广为任意作业稳定。
- 不做通用副本导航、自动配队或多设备并行。
- 安装包能构建，不代表安装版完整流程已验收。
- 离线回放通过不等于实机稳定，实机证据也不能覆盖未测试的从者和画面。

具体结论始终看[当前状态](status.md)。
