# Spec: 后端重构 —— 统一执行器并接入桌面端

Status: ready-for-agent

## Problem Statement

我在 UI 里编好队、排好每面的技能和宝具，点"开始运行"之后什么都不会真的发生：运行面板是演示数据，桌面壳只登记了一个状态，真正能刷本的 Python 原型和 UI 完全不通，而且只认我写死的那一个作业、那一台模拟器。作业保存还依赖开发服务器，打包后就丢。我需要一个能从 UI 一键运行任意作业、过程可见、出错安全停下的桌面工具。

## Solution

把执行能力收敛成一个 Python 执行器：它读取作业 JSON，按画面状态机驱动设备，完整执行多面多回合动作，失败即安全停止并留存证据。桌面壳负责启动/停止这个执行器并把运行状态推给前端；作业读写也交给桌面壳，不再依赖开发服务器。前端的编队、编排、导入功能保持原样，只把"运行"和"运行记录"从演示数据换成真实数据。

## User Stories

1. 作为玩家，我想在 UI 点"开始运行"后看到模拟器真的开始刷我选中的作业，这样我不需要打开命令行。
2. 作为玩家，我想在运行面板看到当前是第几面、第几回合、正在执行哪个动作，这样我能判断它有没有卡住。
3. 作为玩家，我想随时点"停止"让执行器立即停下，这样我能随时接管。
4. 作为玩家，我想执行器严格按作业的多面多回合动作执行，而不是只执行每面第一回合，这样我排的长线作业才有效。
5. 作为玩家，我想技能目标、御主技能目标、换人、宝具卡序都按作业执行，这样 3T 作业不会因为放错目标而失败。
6. 作为玩家，我想一面没清场时按我配的补刀策略继续打，而不是卡死或乱点。
7. 作为玩家，我想执行器只按识别到的画面状态行动，识别不了就停下，这样它不会在我的号上盲点。
8. 作为玩家，我想遇到 AP 恢复页时执行器直接停止，绝不替我消耗苹果或圣晶石。
9. 作为玩家，我想误入从者详情、冠位编队页或任何意外弹窗时执行器停止并保存截图，这样我能事后查清楚。
10. 作为玩家，我想在 UI 选择设备和作业，而不是改环境变量或改源码。
11. 作为玩家，我想作业保存在打包后的桌面版里也能用，这样我不必一直开着开发服务器。
12. 作为玩家，我想运行记录是真实数据（时间、作业、结果、耗时、日志位置），这样我能追溯每一次运行。
13. 作为玩家，我想助战选择按作业要求找对应从者，找不到时刷新列表，仍找不到就停止，这样不会借错人。
14. 作为玩家，我想连续出击和末轮停止的行为可预期：最后一次运行后不多点"连续出击"。
15. 作为玩家，我想每次失败都有日志和截图存档，这样我能把问题反馈给开发者。
16. 作为开发者，我想所有执行器改动都必须通过离线回放，这样我不用每次都消耗 AP 验证。
17. 作为开发者，我想回放用例能覆盖真实故障素材，这样修过的 bug 不会复发。
18. 作为开发者，我想执行器的设备访问只有一个实现，这样修截图或点击问题只用改一处。
19. 作为开发者，我想作业里的坐标与设备分辨率解耦，这样换模拟器不用改作业。
20. 作为开发者，我想项目有版本控制和统一测试入口，这样重构可回滚、可复现。
21. 作为开发者，我想需求、票据、架构决策都有文档基线，这样跨会话开发不会丢上下文。

## Implementation Decisions

- **重写范围（用户已决定）**：只保留前端，其余全部重写——设备访问、执行器、状态机、作业存储、桌面桥接都是新代码。旧后端代码只作为行为参考，不作为新实现的起点，不做渐进式改造。
- **保留前端的连带约束**：作业 JSON version 1 的字段语义、槽位引用方式、`jobs/` 存储位置、图库资源数据契约都必须保持不变，否则"保留前端"不成立。前端唯一必须改的是运行面板与历史页——它们目前是演示数据。
- **验证资产不随代码重写而丢弃**：`captures/` 中的真实截图与既有回放用例是行为规格，不是实现代码。新后端必须用同一批素材通过同等验证，否则无法证明重写后不比旧版差。
- **执行器唯一**：执行器是唯一实机执行入口（语言选择见 ADR-0001，重写决定后该项重新开放评估）。Rust 不实现战斗逻辑。
- **设备访问抽象**：执行器内部只有一层设备接口（截图、点击、滑动、分辨率）。实机实现走 adb；回放实现用假设备。现有原型中的硬编码路径与 serial 变为可配置项。
- **坐标基准**：作业与执行器内部统一使用 1280×720 基准坐标，设备层负责换算；非基准分辨率只允许等比缩放，不做逐分辨率适配。
- **画面状态机**：执行循环由画面状态驱动（menu / support / team / battle / card / result / loading / unknown）。每个动作后必须重新识别确认；unknown 一律安全停止，不允许固定坐标盲点在未知画面上使用。
- **作业编译**：作业 JSON 先编译成执行计划（面 → 回合 → 动作序列），不支持的能力在编译期就明确报错，而不是运行时乱点。作业格式 version 1 保持不变，槽位引用方式不变。
- **策略执行**：补刀策略作为回合内未清场时的选卡规则，支持全局与按面覆盖。
- **桌面桥接**：Tauri 负责启动/停止执行器子进程、转发其状态事件到前端、读取运行记录；同一时间只允许一个运行中的执行器。
- **作业存储**：作业读写由桌面壳命令负责（见 ADR-0002），浏览器预览模式只读。
- **安全策略**：AP 恢复页、苹果、圣晶石相关弹窗一律只停不点；任何"使用道具"的确认都不允许自动通过。
- **证据留存**：每次运行一个目录，含动作日志、失败截图、最终状态；运行记录由此生成。
- **工程基线**：引入版本控制与统一测试入口后再开始重构。

## Testing Decisions

- **唯一主测试缝：回放**。用已采集截图与注入 OCR 行驱动执行器，断言分类结果与动作序列。这是现有做法，继续沿用并扩展，不新增平行的测试体系。
- 好测试只断言外部可观察行为：点了哪里、是否停止、退出码、日志内容；不断言内部函数调用。
- 执行器的设备接口是回放注入点，实机与回放共用同一份执行逻辑。
- 每个修复过的实机故障必须补一张真实截图或注入用例进回放，防止复发。
- 统一测试入口：一条命令跑全部回放，作为每次提交前的门槛。
- 实机验收是独立环节，由用户在模拟器上执行，按验收清单核对退出码、日志与最终画面；未通过实机验收不得标记为稳定。

## Out of Scope

- 多设备并行、批量账号管理。
- 任意副本的自动导航与自动配队；关卡入口仍由用户手动进入。
- 非 1280×720 分辨率的专门适配。
- iOS、真机、云同步、账号体系。
- 作业格式 v2（如锁卡语义扩展、条件分支）——本轮只把 v1 执行完整。
- 前端编队与编排 UI 的重新设计。

## Further Notes

- 现有原型已验证的实机行为（助战列表刷新、冠位页停止、连续出击时序、AP 恢复停止）是回归基线，重构后必须逐一在回放中保留。
- 旧后端代码在新执行器通过同等回放与实机验收前保留在仓库中，仅作行为参考，不再维护、不再修 bug。
