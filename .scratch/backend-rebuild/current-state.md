# 项目现状分析（2026-11-19）

产品：HugoFgo，FGO 自动刷本桌面工具。

结论：前端接近可用，"后端"实际是三套互不相通的代码，真正能刷本的只有一个命令行 Python 原型。

**2026-11-19 用户决定：只保留前端，其余全部重写。** 旧后端代码不再做渐进改造，仅作为行为参考；截图素材与回放用例作为验证资产保留。

## 1. 前端：完成度高，可保留

- 编队编辑、从者/概念礼装/御主礼装选择、再临切换、助战指定与同名从者消歧。
- 战斗编排：多面多回合动作、宝具卡序、固定卡序、补刀策略（全局 + 按面覆盖）。
- Chaldea 分享链接导入与作业 JSON 导入导出；作业库读写 `jobs/`。
- 图库资源管线（atlas / equips / 资源中心）。

**缺口**：`RunOverlay` 是写死的演示数据（"阿尔托莉雅 · 一技能"、`00:18`、`BATTLE 1/3`），运行记录历史页同样是写死的两条；设置页明确写着"图像识别运行时：未接入"。也就是说 UI 上的"开始运行"目前不会产生任何真实行为。

## 2. 后端 A：Tauri / Rust 壳

- 可用：设备枚举、设备信息、截图、归一化坐标点击。
- `start_run` 只登记一个 `RunStatus`（状态 `prepared`），`stop_run` 只清状态；代码注释已写明"真正的战斗循环在后续执行器阶段接入"。
- 没有作业读取、没有执行循环、没有状态推送。

## 3. 后端 B：Vite 开发服务器中间件

- `/api/jobs` 读写 `jobs/`（含文件名清洗与路径逃逸检查），`/api/resources` 触发图库脚本。
- 只在 dev server 存在，**打包成桌面应用后作业保存能力消失**。

## 4. 后端 C：Python 原型（唯一能真实刷本的部分）

- `scripts/farm_ember.py`：OCR + 模板状态 + 坐标动作，实机跑通过种火副本，有完整日志。
- `cv/state_classifier.py`：menu / battle / card / result 四类模板匹配。
- `cv/replay.py`：36 个离线回放用例，覆盖助战、好友申请、连续出击、AP 恢复停止、攻击动画干扰等真实故障。
- 硬编码：adb 路径、设备 serial、1280×720 坐标、助战名、职阶页坐标、固定补刀选卡顺序。
- 作业支持度：只读每面**首回合**动作，多回合、换人、锁卡、通用宝具识别都不支持。
- 与 UI / Tauri 零连接，作业路径靠环境变量传入。

## 5. 工程风险

- **项目不是 git 仓库**，重构不可回滚，这是当前最大的风险。
- 没有统一测试入口：`package.json` 没有 test 脚本，回放要手动跑。
- `captures/`、`logs/` 大体积素材没有版本与清理策略。
- `HANDOFF.md` 是唯一文档，是 17 节流水账，没有需求基线与架构基线。

## 6. 保留 / 重构 / 废弃

| 类别 | 内容 |
| --- | --- |
| 保留 | 编队与编排 UI、作业 JSON v1、Chaldea 导入、图库资源管线、CV 模板与回放体系、已采集截图素材 |
| 重构 | Python 原型 → 状态机执行器；Tauri 壳 → 进程管理 + IPC；作业存储 → 桌面壳命令 |
| 废弃 | RunOverlay 与历史页的演示数据、Vite 中间件的 jobs API、执行器中的硬编码设备与坐标常量 |
