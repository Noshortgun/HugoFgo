# 66: 指令卡多帧识别与空槽未知卡防护

**Status:** ready-for-agent
**Blocked by:** None

## Problem Statement

实机运行在第 1 面连续暴露两类选卡错误。第一次，执行器在指令卡飞入时只看到五张普通卡的外形，五张从者身份均为未知，立即以“可用指令卡不足三张”停止。第二次，希耶尔锁卡使五张普通卡全部属于希耶尔，作业要求宝具前后优先使用红卡，执行器却提交了一张红卡、宝具和一张蓝卡。

五张卡同属一个从者时，从者优先级不会造成颜色差异，因此不能把问题归因于作业排序。现有证据指向飞卡动画和单帧误识别：中间帧被过早当成可提交手牌，且运行日志只保留最后选中的三张卡，没有保留全部五卡的识别结果，复盘证据不足。

编队存在空槽位时还有额外风险：未知卡可以作为空槽实际任意从者的卡参与补刀，如果只给单帧未知一个“首帧直接提交”的机会，指定从者被误认成未知后，就可能被错误地降级为任意从者并选中。

## Solution

执行器应把飞卡过程中的画面当作识别样本，而不是立即可执行的选卡结果。首张无未知、无冲突的完整手牌仍立即选择，保持正常速度；一旦出现未知身份或前后识别冲突，就按卡位汇总连续帧结果，以多数结果决定从者与颜色，而不是要求画面像素完全一致，也不依赖固定长时间等待。

出现未知身份时至少结合三帧结果。空槽存在时，单帧未知绝不能直接作为任意从者提交；后续多数证据明确为指定从者时必须恢复指定身份，只有连续多帧仍未知时才保留空槽任意从者语义。指定从者与空槽任意从者的两层优先顺序保持不变。

提交三卡时同时记录全部五张普通卡的从者与颜色，使用户和开发者在下一次实机运行后能直接核对“实际手牌、识别手牌、最终三卡”是否一致。持续无法形成可靠结果时仍安全停止，不猜测、不盲目点击。

## User Stories

1. 作为自动刷本用户，我希望程序不要在卡片飞入时立即停止，以便卡片停稳后能继续原作业。
2. 作为自动刷本用户，我希望程序不要在飞卡中间帧直接提交，以便瞬态识别不会变成真实点击。
3. 作为使用希耶尔锁卡的用户，我希望五张卡同属希耶尔时仍严格按颜色倾向选择，以便宝具前后都使用红卡。
4. 作为使用红卡优先策略的用户，我希望单帧把红卡误认成蓝卡时程序不要马上选错，以便后续正确帧能纠正结果。
5. 作为用户，我希望程序比较每张卡的从者和颜色，而不是比较画面像素，以便卡片轻微来回移动不会阻止执行。
6. 作为重视执行速度的用户，我希望首张已经完整且无异常的手牌立即提交，以便多帧防护不拖慢正常流程。
7. 作为编队含空槽位的用户，我希望真正的任意从者卡仍能参与补刀，以便既有空槽规则不被多帧确认破坏。
8. 作为编队含空槽位的用户，我希望单帧未知不能直接作为任意从者提交，以便指定从者不会因一次误识别被降级。
9. 作为编队含空槽位的用户，我希望后续多数证据能恢复指定从者身份，以便指定从者优先级仍然正确。
10. 作为用户，我希望身份和颜色持续无法确认时程序安全停止，以便不会用猜测结果继续战斗。
11. 作为复盘运行证据的用户，我希望日志保存全部五卡的识别结果，以便判断是识别错误还是排序错误。
12. 作为维护者，我希望真实故障帧和锁卡场景进入统一回放，以便后续修改不会重新引入同类问题。
13. 作为维护者，我希望技能冷却确认与手牌多帧识别分别验证，以便技能未生效和选卡误识别不会被混为一谈。
14. 作为维护者，我希望文档明确正常路径、异常路径、空槽语义、超时和实机未验收项，以便不把离线通过误写成实机稳定。

## Implementation Decisions

- 在执行器的选卡边界增加手牌读取历史，按画面中的卡位记录从者槽位和卡色，不比较像素位置，不要求连续帧完全相同。
- 首张完整手牌若没有未知身份且能够直接选出三卡，沿用原有立即提交路径，不增加固定等待。
- 需要多帧确认时，对每个卡位分别取多数结果。单次未知或单次错误颜色不能独自决定提交。
- 任一读取历史出现未知身份时，至少使用三帧；未形成多数或平票时继续等待，直到动作超时。
- 空槽任意从者规则不改为“指定从者优先”或“未知一律禁止”。未知身份经过多帧确认后仍可属于空槽实际从者，且仍处于指定从者之后。
- 单帧未知无论编队是否有空槽，都不得直接提交。后续多数结果若指向指定从者，必须恢复该指定身份。
- 宝具区域继续沿用已有的稳定确认和位置映射，不与普通卡投票混为一谈。
- 三卡提交事件增加全部五张普通卡的从者与颜色，保留原卡序、批次、恢复次数、实测间隔与后续画面确认。
- 技能冷却确认使用独立判据：技能图标进入冷却后才能推进下一技能；该逻辑不改变手牌投票，也不把“技能已点击”当作“技能已生效”。
- 计划外自动战斗的技能执行路径尚未实现，不在本票虚构其覆盖范围。未来实现必须同样满足“冷却技能不点击、上一技能未确认不得继续”。

## Testing Decisions

- 最高测试边界放在执行器场景：输入战斗页、连续选卡页和攻击动画，断言真实动作事件，不只测试一个孤立的排序函数。
- 使用统一离线回放覆盖完整动作链，沿用现有执行器测试和关键帧回放方式，不连接真实设备。
- 使用真实飞卡故障截图验证“第一帧身份未知时等待，后续可识别后提交普通卡、宝具、普通卡”。
- 使用五张同属希耶尔的手牌验证“单帧误认一张红卡为蓝卡时，后续多数结果仍选择两张红卡”。
- 使用含空槽位的编队验证“单帧未知不得提交，后续指定从者多数结果恢复指定身份”。
- 使用持续未知或持续不足三卡的场景验证超时停止，不把等待改成无限循环。
- 使用既有普通手牌场景验证无异常首张仍立即提交，避免把多帧防护变成每次固定等待。
- 技能部分使用冷却图标真实截图和执行器场景，验证梅林一技能未确认时只重试一技能，不执行二技能。
- 验证命令为执行器完整单测、统一回放和项目完整验证；实机结果单独验收，不用离线通过代替。

## Out of Scope

- 不实现计划外自动战斗的技能、宝具、告知或退场预览功能。
- 不改变作业 Schema、固定宝具卡序、从者与空槽任意从者的两层优先级。
- 不识别技能伤害、NP 数值或实际战斗效果，不把冷却确认扩展成伤害确认。
- 不为消除所有等待而引入固定长时间延迟；正常无异常首帧仍立即选择。
- 不承诺全部从者、全部再临和全部特效下的识别泛化，感知留出集仍按原票据验收。
- 不把离线测试通过写成实机稳定；本票合并后仍需指定作业实机复验。
